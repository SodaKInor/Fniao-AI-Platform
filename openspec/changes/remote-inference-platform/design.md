## Context

动机见 [proposal.md](proposal.md)，原始源码与配置审计见 [audit.md](audit.md)。现有实现为 Vue 2、Java 8 / Spring Boot 2.6.6、MySQL、Redis和本地上传存储。

2026-09-03 确认的条件：开发阶段两台电脑处于同一局域网，GPU 电脑为 Ubuntu + RTX 5070；正式 GPU 服务器为 Ubuntu + 单张扩容至 48GB 的 RTX 4090。GPU 端由另一位同事开发维护，本项目只负责发请求、接收成果及业务处理。显卡/运行时信息用于交付方环境记录，不作为本项目的实现内容。

本文是待实施设计。接口路径与 JSON 示例属于建议契约；同事若已有接口，以双方确认版本为准，由本项目适配层转换。

## Goals / Non-Goals

**Goals:**

- 前端通过业务后端完成提交、等待、结果查看和下载。
- 同事替换模型或迁移 GPU 服务器时，前端业务接口保持稳定。
- 输出成果回存到业务系统后，GPU 服务离线不影响历史查看。
- 清楚区分已完成、失败、结果未确认和外部接口未支持的操作。

**Non-Goals:**

- 不在本项目开发或部署 GPU 服务，不规定同事使用什么算法、语言、模型框架或内部队列。
- 不假设同事已提供任务查询、取消、回调或请求去重；这些属于需确认的可选接口能力。

### 3. 局域网通信

首期由管理机后端主动访问 GPU 电脑的固定局域网 IP/域名和端口；输入文件和返回成果沿这条调用链传输。建议用 DHCP 预约或静态地址固定 GPU 地址。实际 IP、端口与健康接口由同事提供，不使用旧源码中的作者地址。

GPU 服务需监听管理机可达的网卡/端口，并配置相应主机防火墙/容器端口。我们从后端容器检查可达性，再发送测试素材；ping 不能代替应用请求验收。同事无需读取我们的 MySQL、Redis或文件卷，也无需连接管理机 localhost。

管理页面若仍只在管理机浏览器使用，可继续监听 127.0.0.1:8080。只有其他设备需要打开前端时，再调整前端监听与权限入口。开发与正式使用相同调用代码，分别配置服务地址、凭据和请求限额；生产服务器网络位置尚未确定。

服务鉴权独立于用户登录，凭据只保存在后端。受控局域网测试可使用 HTTP 与测试素材；真实业务素材传输使用验证过的 HTTPS 或等效加密通道。双方确认健康接口可见内容和访问凭据，不要求开放完整内部监控。

### 4. 与同事约定的最小接口

优先对接一次请求返回成果的 HTTP 接口，不要求对方先实现完整任务平台。若已有接口，则用适配器映射下列语义。

| 必须约定 | 需要写清的内容 |
|---|---|
| 服务地址 | 开发/正式 base URL、调用路径、HTTP 方法、协议版本 |
| 鉴权 | Header 名称、凭据获取与轮换方式 |
| 请求身份 | request_id；对方是否回显、是否据此去重，保留窗口多久 |
| 输入 | 文件上传或 JSON，支持的媒体、大小限制、业务参数 |
| 成果 | 返回 JSON、文件流或成果下载引用；字段类型、文件类型、保留期限 |
| 失败 | HTTP 状态、业务错误码、错误说明及是否可重试 |
| 时间 | 典型/最大处理时长、连接/处理/传输超时和并发限制 |

推荐文件输入使用 multipart/form-data：file 字段传文件，metadata 字段传 JSON，避免向对方发送本地绝对路径。对方如要求 URL 拉取，再单独解决文件访问地址与授权；首期文件直传避免反向可达配置。

以下仅为交接讨论示例，不是已确认可调用的地址：

```text
POST /infer
Authorization: Bearer <service credential>
Content-Type: multipart/form-data
file: <input file>
metadata: <JSON below>
```

```json
{
  "request_id": "req_01",
  "capability": "image-analysis",
  "parameters": {}
}
```

推荐 JSON 成功响应：

```json
{
  "request_id": "req_01",
  "status": "succeeded",
  "output": {
    "type": "image",
    "data": {},
    "artifacts": [
      {"id": "result_01", "media_type": "image/png", "download_path": "/results/result_01"}
    ]
  },
  "metadata": {"service_version": "1.0"}
}
```

output.type 可以为 text/image/video/json；具体能力的 data 字段必须有结构定义。返回检测坐标时，约定原图尺寸、坐标单位和必要帧时间，属于结果解释契约，不涉及算法实现。模型 ID/版本等信息若对方提供则如实记录，不提供时标为未提供，不自行推测版本。

对方也可直接返回二进制成果，适配器依据已确认的 Content-Type 转成我们的资产记录。若返回文件引用，优先使用同一服务下的相对下载路径；不接受 GPU 本地磁盘路径。第三方成果地址需要明确允许的主机、协议与访问方式，禁止任意 URL/重定向导致后端越界下载。

异步提交/查询、取消、回调、请求去重、模型元数据发现都是可选扩展，以对方明确提供为准。我们优先采用主动请求/查询模式；不把回调作为首期依赖。

### 5. 本项目的前端接口

前端统一访问 /jeecg-boot/ai/v1，沿用当前登录身份：

| 接口 | 作用 |
|---|---|
| GET /capabilities | 本项目开放的业务能力及可用性、输入限制 |
| POST /assets | 上传并建立私有资产记录 |
| POST /infer | 提交业务请求并在短等待预算内返回；超预算返回本地任务 ID |
| POST /jobs | 需要后台等待时立即返回本地任务 ID |
| GET /jobs/{id} | 查询本地执行状态与已保存成果 |
| POST /jobs/{id}/cancel | 仅取消尚未派发任务，或调用对方明确支持的取消接口 |
| GET /assets/{id}/content | 按归属授权下载 |

前端不接收或指定 GPU URL、服务密钥、算法路径。后端适配器将同事的错误/成功响应转换为现有 Result 外层下的稳定数据结构，区分空成果、处理失败、服务离线、超时与格式错误。GPU 鉴权失败是服务配置错误，不应让业务用户退出登录。

### 6. 等待、超时与重试

同步返回是外部接口的默认对接方式。为了避免前端长时间挂起，本项目可以先保存调用记录，由后台执行器调用同事的同步接口；前端等待预算内完成返回 200，尚未完成返回 202 和同一条本地任务 ID。这不改变同事的请求/返回实现。

外部响应为 202 且提供任务查询时，适配器保存 provider_task_id 并按约定查询。本地异步与外部异步明确区分，不能凭返回一个本地任务编号声称对方支持远程任务恢复。

建议状态：

```text
PENDING -> DISPATCHING -> WAITING -> FETCHING_RESULT -> SUCCEEDED
   |             |            |
   |             +------------+--> FAILED / UNKNOWN
   +--> CANCELLED
```

- 返回已受理前保存任务 ID、用户归属、输入、服务配置快照和请求参数。
- 浏览器重复提交：同用户幂等 key + 相同请求摘要返回同一记录；不同输入复用 key 返回冲突。
- 外部请求发出后断线/超时：如果对方支持按 request_id 查询则对账；如果不支持，标为 UNKNOWN（结果未确认），不自动再次执行模型。
- 后端重启：恢复未派发任务；已派发且无法向对方查询的任务保留 UNKNOWN。不能承诺恢复已断开的同步请求或保证外部绝不重复执行。
- 自动重试仅用于已确认安全的操作，或对方明确定义了幂等行为的同一请求；HTTP 500 本身不能证明可安全重复推理。
- 用户刷新页面不重新提交。明确重试 UNKNOWN 记录时保留原记录和新尝试身份，提示可能已处理，按业务规则执行。
- 取消 PENDING 任务可由本项目完成。已发送任务若对方不支持取消，显示不能停止外部处理；关闭页面/终止 HTTP 等待不等于 GPU 已停止。
- 有对方取消能力时等待确认再标为 CANCELLED，迟到结果不得覆盖已确定终态。

### 7. 成果保存与数据结构

输入使用私有 assetId 管理，保存归属、MIME、大小、内容哈希和保留期限。新 AI 资产不允许经旧匿名静态路径绕过权限下载。上传与成果取回采用流式读写及限额，避免把整个大文件读入内存。

收到外部成果后：校验响应结构/媒体 -> 受控下载或保存文件流 -> 检查传输完整性（对方提供长度/哈希时核对）-> 在本地计算并保存内容哈希 -> 保存结构化结果和元数据 -> 标记成功。获取成果失败保留 FETCHING_RESULT/明确错误，不提前显示成功。文件引用的有效期和鉴权方式需双方约定，不能仅把临时 GPU URL 存成永久业务成果。

建议最小数据模型：

| 对象 | 内容 |
|---|---|
| 服务配置 | 开发/正式地址、凭据引用、协议/适配器标识、已确认的可选能力 |
| 业务能力绑定 | capabilityCode、服务/外部能力或模型标识、输入输出约束、启停状态 |
| ai_asset | 归属、内部存储键、MIME、大小、哈希、保留期 |
| ai_job | requestId、归属、输入、参数/绑定快照、本地状态、可选外部任务 ID、错误和结果元数据 |
| 必要状态事件 | 变更时间、来源、去重身份；由本项目生成，不强求对方提供事件流 |

旧模型退役在本项目指停用业务绑定、关闭旧本地执行和清理不需要的菜单/依赖。GPU 权重与模型的删除、替换和部署属于同事的工作。历史结果保存当时已知的能力、参数和对方版本信息，不依赖旧本地权重仍存在。

开发配置对接局域网 Ubuntu RTX 5070 服务；生产配置对接 Ubuntu 单卡 RTX 4090 48GB 服务。GPU 驱动、运行镜像、批量、精度和显存限制由同事维护；我们以双方确认的响应成果和接口容量验收。

## Risks / Trade-offs

- [对方只有同步接口] -> 本项目可后台等待，但网络中断后的远程执行状态不能凭空恢复，显示 UNKNOWN 并禁止盲目重发。
- [对方输出为临时 URL] -> 明确有效期与鉴权，及时回存到本地，避免历史结果随 GPU 临时文件消失。
- [对方取消/幂等能力未提供] -> 按实际接口能力展示操作，不对用户承诺未实现的语义。
- [开发/正式模型成果不同] -> 双方分别提供符合相同契约的代表性样例，正式发布完成真实成果验收；不由本项目调试内部算法。
- [旧匿名接口和旧本地调用仍在] -> 后端执行守卫与权限先行，前端入口同步收敛。

## Migration Plan

### 分批原则与当前进度

2026-09-03 按用户要求将实施拆为以下 8 批。当前完成规划、任务目录、Git 基线和独立 worktree 准备；1.3 已完成，其余任务按实际验收推进，远程业务与真实联调仍未完成。详细任务和勾选进度以 [tasks.md](tasks.md) 为准。

一批是一个可验收的交付单元，不等同于一天或一次对话。按用户最新要求，实施单元改为独立目录中的工作包，每包有自己的分支，最终汇入同一集成分支；不使用符号链接或硬链接共享可写源码。各包只执行分配任务，通过 HANDOFF.md 提交结果，集成任务核实后更新 OpenSpec 总表。新对话不自动继续执行其他包的任务，也不因单包完成就归档整个变更。

保留现有 Vue / Java 技术栈，先增加远程接入模块。GPU 服务、算法和运行环境始终由同事负责。首条流程先用“一个文件输入，返回结构化信息和成果文件”的模拟样例验证通道，该样例不是实际算法选型；正式保留哪个业务入口，在真实接入前写入接口记录。

### 依赖与等待处理

验收里程碑仍为 1 → 2 → 3/4 → 5/6 → 7 → 8，开发则按工作包依赖并行。第 1 批建立 Git 基线和隔离工作区；第 2 批提交公共契约及最小共享类型，由 00 集成后记录共同起点；03 客户端、04a 文件/任务后端、04b 前端从同一起点并行。00 按依赖合并并完成 4.7 后，05 可做真实联调，06 可做本地恢复及故障验证，08 可准备发布资料；05/06 若需要修改同一文件则由 00 先分配归属并串行合并。07 的删除操作等待真实联调及稳定性验收完成，08 的正式验收等待发布候选和正式服务可用。

第 2 批区分“我们完成并冻结用于开发的契约”和“双方确认真实服务契约”，后者必须在第 5 批完成，不能因为生成了文档就标记已获同事确认。若真实接口变化，先由契约所有者更新约定并集成，再调整受影响工作包。

若同事接口尚未就绪，先完成第 1—4 批，并可继续第 6 批中不依赖真实服务的故障模拟和本地恢复工作。第 5 批保持未完成，不用模拟测试代替双机联调，也不提前删除尚未验证替代链路的旧代码。正式服务器尚未提供时，可准备第 8 批发布资料，但保留真实接入验收为未完成。

### 每批完成标准

1. 完成该批的具体交付与任务内验收，只勾选已有证据的任务。UI 演示、模拟调用和真实跨机调用分别记录，不能相互替代。
2. 每个工作包在自己的 HANDOFF.md 记录任务子项、变更文件、基线/交付提交、验收结果、接口版本、限制和回退方式。集成者核实后更新总表；版本化验收材料按工作包分别保存在 backend-github/integrations/ai-contracts/acceptance/<工作包>/，不含凭据或真实敏感素材。
3. 代码和部署增量只修改 backend-github / frontend-vue；根目录仅涉及必要 Git 元数据、忽略规则和 OpenSpec 规划文件，backend-master 不修改。数据库使用增量迁移，不清空现有表。
4. 代码改动后在实际代码 worktree 更新 Graphify，并复核提交范围；现有 tools/graphify/update 硬编码原 WGAI 路径，工作包必须直接在自己的 code 根执行 graphify update .，不得借脚本改写原目录。共享 Serena 服务未确认作用于本 worktree 时不通过它写入或切换全局项目，使用本目录文件操作并记录原因；不新增第二个 Serena MCP 服务。
5. 原仓库保存基线，各工作包在独立分支提交，00 负责汇入 feature/remote-inference 等集成分支并记录验收点。合并前检查契约版本、归属范围、架构规则和运行资源隔离；不自动创建远程仓库或对外发布。

### 验收深度与回滚

权限检查、旧本地执行守卫、文件限额、私有成果、持久调用 ID、本地提交去重和“结果未知不盲目重发”在第 3、4 批建立，进入第 5 批真实调用前已生效。第 6 批补全恢复/取消等行为并做系统性故障验证，不是到第 6 批才开始保护真实请求。第 5 批为受控联调，第 6、7 批通过后才进入首期发布候选。

分别验证正常响应、有效空成果、超限输入、外部凭据错误、慢响应、格式错误、临时下载引用、下载中断、重复提交、响应丢失、后端重启、跨用户访问和已完成成果离线可读。优先在本地协议夹具注入故障，不擅自停止同事的 GPU 服务。查询/取消未提供时验证明确的不支持行为，不将可选能力当必做的对方实现。

第 1 批记录数据库/资产的一致备份与来源，第 4 批在数据库副本检查增量迁移，第 8 批在隔离环境实际恢复并检查记录/文件能对应。对外部响应只做契约与成果可用性验收，算法质量、显存、驱动和 GPU 内部性能由同事负责。

代码或配置故障时优先设 AI 模式为 disabled，保留管理和历史查询；需要回退时使用与当前数据结构兼容、已具备远程执行守卫的上一业务版本。不自动降回可执行旧本地模型的原始基线，不删除数据卷，不重跑首次初始化清理 SQL。旧依赖在第 7 批按清单分组清理，每组保留回退提交；不自动删除历史记录、用户素材或同事的模型文件。

### 首期之后

Vue / Java 大版本升级、持续视频、问答流、训练业务以及新增成果类型分别按业务需求另列变更。第 8 批交付时记录这些后续事项，不把它们当成本次完成的必要条件。
