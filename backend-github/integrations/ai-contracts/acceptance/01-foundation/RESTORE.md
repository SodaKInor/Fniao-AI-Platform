## 隔离恢复操作顺序

以下是后续恢复步骤，不是本轮生产恢复授权；不得把目标指向 `wgai` 项目、原数据库卷或原上传卷。

1. 从有效目录读取 manifest.json，重算四个归档 SHA-256；检查 uploads.tar、redis.tar 的私有成员清单。缺少 PASS manifest 的准备目录均不可作为有效备份。
2. 使用新的项目名、仅本机端口、新数据库和新命名卷。先检查配置渲染结果和真实资源是否均属于恢复项目，再启动任何容器。
3. 使用 `docker load` 读取 images.tar，以回执 saved_image 标识选择镜像。原始镜像标识用于审计，不能对已不存在的镜像强行恢复；不得改写原 local 标签。
4. 数据库恢复使用匹配的 MySQL 8.0.36。若使用保存的旧 MySQL 快照，其首次初始化目录可能含历史原始 SQL；启动空恢复库时必须用本次导出的数据库替换初始化内容，禁用旧的 002-local-sanitize.sql，或使用同版本官方 MySQL 空镜像先初始化空库。
5. 在新空数据库导入 database.sql.gz。该导出含 CREATE DATABASE / USE java_ai：保留该库名时只连接新隔离 MySQL；改库名时只调整数据库选择语句，不对数据内容做全局文本替换。本包隔离脚本仅在空测试库执行这种导入。
6. 将 uploads.tar 解开到新上传卷，保留所有者和权限；逐个核对成员哈希。不得将归档解压进原卷。根据 private/container-config.json 确认原上传挂载位置 `/data/uploads`。
7. 按需要恢复 Redis 到新卷；不能把旧队列内容自动重新派发为外部推理。恢复服务凭据只从 private/ 读取，或为新实例重新生成并同步连接配置，禁止粘贴进交接材料。
8. 先启动数据库与 Redis，再启动后端与前端。检查核心健康、权限、记录与上传文件对应关系，以及所需历史页面。登录和业务恢复验证仍需对应用户授权与真实验收。

本轮对备份做了读取、数量和校验验证；运行资源检查使用隔离数据库副本，不等于第 8 批完整恢复与回滚验收。原生产卷从未作为恢复目标。
