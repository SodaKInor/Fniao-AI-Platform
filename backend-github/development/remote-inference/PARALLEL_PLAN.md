# 独立目录并行实施

## 工作方式

原 WGAI 保存源码基线与 Git 共享仓库。任务入口位于同级 WGAI-parallel/，每包包含独立说明和 code/ 工作树：

```text
WGAI/                          原始工作区 / 仓库基线
WGAI-parallel/
  README.md
  WORKSPACES.json
  00-integration/               合并、总体验收、总进度
  01-foundation/                基线、备份、隔离工作区
  02-contract/                  契约和共享类型
  03-client/                    远程请求客户端
  04a-assets-jobs/              文件、任务和成果后端
  04b-frontend/                 页面与组件
  05-lan/                      双机真实联调
  06-resilience/               故障、恢复和取消
  07-cleanup/                  旧业务迁移与清理
  08-release/                  正式接入
```

每包独有 START_HERE.md、AGENTS.md、TASKS.md、HANDOFF.md；code/ 必须由 Git worktree 创建，不是指向 WGAI 的共享软链接。不同目录的分支共享 Git 对象历史，不共享可写源码。任务说明已经存在不等于 code/ 已就绪。

## 启动顺序

1. 01-foundation 建立经检查的 Git 基线、备份和工作区。02-contract 可以同时在自己的 drafts/ 中整理文档草案，但基线形成前不修改原项目代码。
2. 02-contract 提交 2.1—2.5 的契约、样例和最小共享类型；00 合并并登记同一个契约提交。
3. 03-client、04a-assets-jobs、04b-frontend 从这个共同提交开始并行开发。它们分别用协议夹具、端口测试替身和业务 API 模拟验证，不能把测试替身放入正式运行模式。
4. 00 先合入客户端和文件/任务后端，再合入前端，完成任务 4.7 的真实组合模拟闭环，并检查任务 3.4 的前后端两部分。
5. 05-lan 做真实联调，06-resilience 做恢复与本地故障验证；08-release 可写发布资料。按 FILE_OWNERSHIP.md 分配文件，冲突处先串行交接。
6. 05 和 06 通过后，07-cleanup 迁移并清理旧实现；08 的真实正式验收等待此发布候选与同事正式服务就绪。

原 8 批是验收里程碑，10 个目录是开发分工，两者不是一一对应：第 4 批拆为 04a、04b，4.7 由 00 集成执行。不要在 04a 对话里执行 04b 的任务，也不要创建 8 个同时修改同一源码目录的对话。

## 分支与集成

建议 00 使用 feature/remote-inference，其余包使用 work/remote-inference/<包名>。主工作区保留 main 基线。所有包记录起点提交与当前契约提交，不能只记录一个可能移动的分支名。

分支先准备好但前置契约尚未合入时，包仍处于等待状态；开始编码前，在干净工作树中合入 00 已验收的公共起点。已有未提交内容时先保存与说明，不自动 reset、强推或覆盖。

交付顺序：包提交自己范围的代码与证据 → 写 HANDOFF.md → 00 检查路径、契约和验收 → 合入集成分支 → 必要的组合验证 → 更新 OpenSpec 总表。后续包从已验收提交继续。公共图谱/验收文档冲突由 00 重建或整理，不通过任意选择一边来吞掉信息。

本地工作不要求创建远程仓库、推送、发送消息给同事或自动创建新的 Codex 对话。用户自己选择目录新建对话。

## 运行资源必须隔离

每包有独立的测试数据库/目录、临时文件和宿主机端口。WORKSPACES.json 中的端口只是候选登记，启动前检查占用。

现有 Compose 可能包含固定 container_name、命名卷或外部卷，单独设置项目名不足以保证隔离。每包只在自己的 backend-github/deploy/remote-ai/ 下创建必要覆盖配置，并检查渲染后的容器名、端口、卷、挂载和数据库连接全部指向本包；不直接运行会操作原 WGAI 数据的启动、重置或清理脚本。不挂载原业务卷做可写测试。

共享不可变依赖缓存可以复用，不共享 node_modules、target、dist 或可写上传目录。不得把服务凭据提交到分支或交接文件。

backend-master 保持只读参考，不复制进改造提交。任何工具返回原目录路径时，先检查它是否只是只读参考，不能按返回路径直接写入。

## 状态与交接

- PREPARED：任务说明已创建，尚未具备代码工作树或前置条件。
- READY：该包所需的工作树和当前阶段条件已具备；若属于实现包，还必须核实公共契约起点与运行资源。
- WAITING_PREREQUISITE：代码 worktree 已创建，但前置契约/集成验收尚未具备，不能直接开始实现。
- IN_PROGRESS：仅本包正在实现。
- READY_FOR_INTEGRATION：代码已提交，包内验收完成，等待 00 合并。
- INTEGRATED：00 已合并并完成相应集成验证。
- WAITING_EXTERNAL：真实接口/服务器/凭据等外部条件未具备；记录具体缺项，先做独立可行工作。

只有 00 根据实际证据更新总任务勾选；各包不自动归档整个变更。尚未有 Git 作者信息或基线提交时，工作区状态必须明确保持 PREPARED，不能声称已经获得隔离代码目录。
